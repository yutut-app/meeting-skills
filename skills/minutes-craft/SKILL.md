# 打合せ議事録の作成

## 役割

自社側の記録担当として振る舞う。最優先は、後から「言った言わない」を起こさない記録を残すこと。
読みやすさは二の次で、**読みやすさのために区別を潰さない。**

| 判断が割れる場面 | どちらを取るか |
|---|---|
| 相手の発言が事実なのか要望なのか曖昧 | **分けて書き、どちらか判然としないものは「要確認」に置く。**どちらかに決めない |
| 合意できたように見えるが条件が付いていた | **未決に置く。**条件付きの合意は合意ではない |
| 素材に書かれていない前提が明らかに見える | **書かない。**「未確認」として残し、利用者に問う |
| 自社に不利な発言が記録に残る | **残す。**自社に有利な方向へ丸めない |

**推測で埋めない。** 素材に無いことを書くと、その議事録は相手と突き合わせたときに崩れる。
崩れたことに気づくのは、相手が指摘したときで、そのときには手遅れになっている。

## 進め方

**1ステップ = 1つの成果物か1つの判断。** まとめて実行しない。
前のステップの出力を示してから次へ進む。要件を一度に渡すと、いくつかが黙って落ちる。

| 手順 | 作るもの・決めること | 完了条件 |
|---|---|---|
| 1 | 素材の種別、会議の基本情報、**書式の出所**、**崩れ候補** | 日付・相手先が埋まり、書式の出所が決まり、崩れ候補が全件判定された（★承認） |
| 2 | 作業スペース | パスが解決し、素材がそこに置かれた |
| 3 | 議事録の本文（md） | 全項目が4値のいずれかで埋まり、未判定が無い |
| 4 | 検査の結果表 | 全検査項目が「合格」か「要確認」で、要確認が利用者に渡った |
| 5 | 渡す形（md / docx / xlsx） | 相手へ出す版を確定した（★承認） |

## 1 素材と基本情報を確定する ★ここで止まる

`references/10_intake.md` を読む。素材が文字起こしか手書きメモかで読み方が変わる。

### 必須と任意

**必須が埋まるまで本文を書かない。** 無いまま進めると、もっともらしい値が埋まって出てくる。

| 区分 | 項目 | 無いとどうなるか |
|---|---|---|
| **必須** | 会議日 | 日付の無い議事録は、後から順序が追えず証拠にならない |
| **必須** | 相手先の名称 | 誰との約束か特定できない |
| **必須** | 素材そのもの（文字起こし or メモ） | 作業が成立しない |
| 任意 | 出席者（氏名・所属） | 既定は「素材から読み取れた範囲」。読み取れない分は「未確認」と書く |
| 任意 | 会議名・議題 | 既定は素材から推定し、推定と明記する |
| 任意 | 前回議事録 | 不在なら「前回からの持ち越し」の節を作らない。不在そのものが情報 |
| 任意 | **書式の出所** | 既定は**このスキルの型**。探す順序は `20_template.md` 1節。既存書式があるのに型を当てると、受け取る側が読む場所を探すことになる |

**必須の3つが揃っていないときだけ聞く。** 任意の項目は既定で進め、
埋めた根拠（素材のどこから読んだか／推定か）を1行添える。

### 書式の出所を決める

**このスキルの型は既定であって、優先ではない。** 相手先や社内に書式があるなら
そちらに合わせる。探す順序と、合わせても落とさない3つは `20_template.md` 1節。

**勝手に型を当てない。** 既存書式を無視した議事録は、受け取る側が
読む場所を探すことになり、章立てを揃えている意味が消える。

ただし**書式に合わせても、区分・出所・要確認の3つは足す。** 書式に列が無ければ
別表として添える。ここを落とすと、言った言わないを防ぐという目的そのものが消える。

**書式を①③で得たときは、`formats/<相手先>.md` に写す。** 次の案件が②で引けるようになる。
**写さないと `formats/` は永久に空で、毎回雛形を渡してもらうことになる。**

| 出所 | 写すか |
|---|---|
| ① 渡された雛形 | **写す。**同じ相手先の次回に効く |
| ③ 過去の議事録から読み取った | **写す。**読み取りをやり直さずに済む |
| ② `formats/` から引いた | 写さない。既にある |
| ④ 無し（スキルの型） | 写さない。相手先の書式ではない |

写すのは**章立て・列・呼称**だけで、**その回の会議の内容は写さない。**
内容を写すと、次の案件で前回の中身が混ざる。

### 崩れた語を洗い出す

**崩れ候補が1件でもあれば `references/15_terms.md` を読む。**
自動文字起こしの誤変換と、手書きメモの略記は、**読める語に化けるため気づかれない。**

やることは3つ。**そのまま載せて終わりにしない。**

1. 崩れ候補を5つの型で洗い出す
2. **案件の分野を特定し、分野の語彙を調べる**
3. **候補を2つ以上出し、合否を利用者に問う**（判定の既定は「未確認」）

**調べたから直してよいのではない。** 確定させるのは利用者で、
候補が1つしか出なかった場合も問うのを省かない。

**崩れ候補が未確認のままでも、議事録の下書きは出す。** 語の確定を待つと、
記憶が新しいうちに相手と突き合わせる機会を失う。下書きを先に出し、並行して確定させる。

### 止まる理由

日付・相手先・出席者は後続すべての前提になる。間違えると本文を全部書き直すことになり、
しかも**間違えたまま相手に出すと、訂正の連絡が必要になる。**

**止まるときは、この時点で未決のものを全部まとめて出す。**
基本情報の確認、**書式の出所**、**崩れ候補の合否**、素材の読み取りで判然としなかった箇所を、
同じメッセージに載せる。承認1件につき1ターンを使わない。

**崩れ候補の合否を別のターンで聞かない。** 承認ポイントはこの1箇所のままにする。
増やすと利用者が承認作業員になる。

## 2 作業スペースを用意する

`references/30_export.md` の「作業スペース」の節を読む。

**議事録と素材はスキルフォルダに置かない。** スキルフォルダは手順を置く場所で、
案件の記録を置く場所ではない。パスはスクリプトで解決する。

```bash
SKILL_DIR=<この SKILL.md があるディレクトリの絶対パス>
cd "$SKILL_DIR" && ./scripts/ws-path.sh <YYMMDD_PJ名>
```

**`cd` を省かない。作業ディレクトリは呼び出しごとに戻るため、相対パスだけでは外れる。**

解決できなかったら**止めて報告する。** 既定の場所へ落とさない。
落とすと書けたことになって、不発に気づけない。

この手順は聞かずに進める。既存の案件ディレクトリがあればそれを使い、
無ければ作って、どちらをしたかを1行述べる。

---

## 3 本文を書く

`references/20_template.md` を読む。**手順1で決めた書式の出所に従って書く。**
既存書式に合わせる場合の規約、事実・要望・留保の分離規約、見本がある。

### 4値で埋める

**すべての項目に、次の4つのいずれかを付ける。「判定不能」を合格に数えない。**

| 値 | 意味 |
|---|---|
| **決定** | 双方が条件なしで合意した |
| **未決** | 議論したが決まっていない。条件付きの合意もここ |
| **要確認** | 素材の記述が曖昧で、どちらとも読める。**利用者に問う対象** |
| **不明** | 素材に記述が無い。**推測で埋めず、この値を書く** |

**「不明」を空欄にしない。** 空欄は「書き忘れ」と区別できないため、
後から読んだ人が「議題に出なかった」と誤解する。

### 判断を出力に出す

判断の結果は、必ず議事録の表の「区分」列に現れる。内部で判断して外に出さない。
**最後に「区分」列が空の行が1行も無いことを確認する。** 残っていたら手順3は完了していない。

---

## 4 出す前に検査する

`references/40_review.md` を読み、**検査の結果を表として出力する。**
検査したと書くだけにしない。やったかどうかが外から見えないため、飛ばされる。

各項目の判定は3値。**既定は「未確認」。**

| 判定 | 意味 |
|---|---|
| 合格 | 確かめて、問題が無かった |
| **要確認** | 利用者に確かめてもらう必要がある。**落とさずに渡す** |
| **未確認** | まだ見ていない。**これが残っていたら手順4は終わっていない** |

**「要確認」を落とさない。** 要確認を削ると、曖昧な箇所が確定したことになって内容が曲がる。
判定を4値にしている理由と同じで、**消すのではなく渡す。**

---

## 5 渡す形を決める ★ここで止まる

`references/30_export.md` の「渡す形」の節を読む。

| 渡すもの | 既定 | 委譲先 |
|---|---|---|
| 議事録本体 | **`minutes.md`** | なし。このスキルで作る |
| 相手先への提出版 | 要求されたときだけ | `docx` スキル |
| 宿題の進捗管理表 | 要求されたときだけ | `xlsx` スキル |
| 中間物（整理前の発言リスト） | **渡さない** | 作業スペースに残すだけ |

**相手へ出す版を確定する直前で止まる。** 外部に出たものは取り消せない。
止まるときは、検査の「要確認」が残っていればそれも同じメッセージに載せる。

### 委譲するときの作法

**docx・xlsx の作り方をここに書き直さない。** 委譲先が持っている機能であり、
2箇所に書くと片方だけ古くなる。渡すのは確定した md と、出力先のパスだけ。

**委譲先の作法と、このスキルの規約が食い違ったら、このスキルの規約を採る。**
食い違った箇所とどちらを採ったかを報告する。黙って片方に寄せない。
実際に起きたのは、記入例として架空の行を求められた件で、
**入れると議事録と件数が食い違う**ため入れなかった。

---

## 完了したら次を提案する

報告して止まらない。次の行動を分類して出し、**推奨を1つ示して理由を述べる。**

| 分類 | 例 |
|---|---|
| A 外に出す | 相手先へ送る版（docx）を作る、社内へ共有する |
| B 次の作業 | 宿題を xlsx にする、次回の議題案を作る |
| **C 調べる** | 前回議事録を探して持ち越しを突き合わせる、相手先の呼称の決めごとを確認する |
| D 前工程に戻る | 素材に欠けがあり、出席者に確認を依頼する |
| E 止める | 相手の確認待ち、社内承認待ち |

**C を忘れやすい。** 要確認が残っているときは、本文を直すより前回議事録を探す方が速い。

---

## 人にしかできない工程

**スキルが自分でやったことにしない。**

| 工程 | 誰がやるか | 依頼の文面と、結果の反映先 |
|---|---|---|
| 素材に無い発言内容の確認 | 出席者本人 | 「<日付>の<相手先>との打合せで、<論点>はどう決まりましたか」と聞く。回答は本文の該当行の区分を「決定」か「未決」に更新する |
| 相手先との認識合わせ | 利用者 | 確定前の md を相手に送って確認を求める。相手の訂正は本文に反映し、訂正された旨を残す |
| 送付・提出 | 利用者 | スキルは出力までで、送信はしない |

**依頼して終わりにしない。** 受け取った結果をどこに反映するかまで上の表に書いてある。

## 外部依存

| 依存 | 要るとき | 無いときどうするか |
|---|---|---|
| `docx` スキル | Word 出力を求められたとき | md のまま渡し、Word 化できないと報告する |
| `xlsx` スキル | Excel 出力を求められたとき | md の表のまま渡す |
| 作業スペースのディレクトリ | 常時 | `scripts/ws-path.sh` が解決できなければ**止めて報告する**。既定の場所へ落とさない |

音声・動画からの文字起こしは**このスキルの範囲外**で、**未検証**。
文字起こし済みのテキストを受け取る前提で作ってある。

## 不一致を見つけたとき

本文に書いてあるパスや前提が、実際と違っていたら**そこで止まる。**
`SKILL.md` と `references/` を直さない。

報告するのは3つ。**直し方は提案しない。**

| 項目 | 内容 |
|---|---|
| 本文の記述 | ファイル名と行、書いてある通りの文言 |
| 実際 | 確認した結果 |
| この案件への影響 | 続行できるか、できないか |

直すのはスキルを作る・直すセッションの役目。使う側が直すと、その案件では正しくても
別の案件で壊れ、しかも原因の台帳に記録が残らず件数が数えられない。

**行き過ぎると:** 止まるだけで何も報告せず、案件が進まなくなる。
**止まるときは必ず上の3項目を出す。** 出せないなら止まらずに続ける。

## 改善プロトコル

このスキルの手順どおりに進められなかった場合、または利用者から出力への指摘を受けた場合、
以下を順に行う。

1. 台帳の表に1行追記する（日付／依頼の要約／期待した挙動／実際の挙動／推定原因）。
   台帳は**スキルディレクトリの2つ上**の `local/docs/feedback.md`。
   追記はこのファイルに対してのみ行う。

2. `SKILL.md` および `references/` はこの時点では書き換えない。

3. 利用者から明示的に修正を求められた場合のみ、`skill-builder` スキルに渡して改訂する。

4. **台帳が存在しない、または書き込めない環境では何もしない。**
   エラーを報告せず、代替手段も取らない。台帳は改訂する側が持つもので、
   スキルだけを受け取った環境には無いのが普通。
