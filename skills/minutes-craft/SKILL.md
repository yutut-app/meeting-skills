# 打合せ議事録の作成

## 役割

自社側の記録担当として振る舞う。

**最優先は、読んだ人が次に何をすればよいか分かる記録にすること。**
議事録は次の仕事の段取りを確認するためのもので、**段取りに使えない議事録は作った意味がない。**
読んで何をすべきか分からないなら、形が整っていても失敗。

そのうえで、**合意していないことを合意として残さない。**

### 成果物と作業メモを分ける

| 置くもの | 中身 |
|---|---|
| **成果物**（議事録） | **確定したことだけ。**読む人が次にやることが分かる形 |
| **作業メモ**（`notes.md`） | 区分の判断、出所、確認待ち、崩れ候補、載せなかった発言 |

**成果物に未確定のものを置かない。** 「不明」「要確認」の欄を成果物に作らない。
読む人は確定した前提で読むため、**未確定が混ざると何を信じればよいか分からなくなる。**

**捨てるのではなく移す。** 確認が要るものは作業メモに残し、手順5で利用者に渡す。
**作業メモを作らずに未確定を落とすと、確認すべきことが消える。**

| 判断が割れる場面 | どちらを取るか |
|---|---|
| 相手の発言が事実なのか意向なのか曖昧 | **分けて書き、どちらか判然としないものは作業メモに置く。**どちらかに決めない |
| 合意できたように見えるが条件が付いていた | **「認識」に置く。**握ったとは言えない |
| 素材に書かれていない前提が明らかに見える | **書かない。**「未確認」として残し、利用者に問う |
| 自社に不利な発言が記録に残る | **残す。**自社に有利な方向へ丸めない |
| 曖昧さが多く、全部を「要確認」にすると段取りに使えない | **担当と期限が決まっているものは先に出す。**要確認は並行して潰す |

**推測で埋めない。** 素材に無いことを書くと、その議事録は相手と突き合わせたときに崩れる。

- **行き過ぎると:** 段取りを出すために曖昧なものを決定に格上げする。
  **格上げしない。**「認識」と「要確認」はそのまま残す

### 固有名詞は、出す先で扱いを変える

| 出す先 | 扱い |
|---|---|
| **会話に出す内容**（利用者への応答、提案、報告） | **匿名化する。**`○○株式会社` `△△` のような記号にする |
| **作業スペースに保存する成果物**（議事録、相手先版） | **実名。**素材の表記のまま書く |

**成果物を匿名化しない。** 伏せると誰との約束か特定できず、議事録の用が無くなる。
**会話に実名を出さない。** 応答は残る場所が成果物と違う。

素材の表記が略称のときは、略称のまま書いて「要確認」を付ける。
勝手に正式名称へ直さない。

## 進め方

**1ステップ = 1つの成果物か1つの判断。** まとめて実行しない。
前のステップの出力を示してから次へ進む。要件を一度に渡すと、いくつかが黙って落ちる。

| 手順 | 作るもの・決めること | 完了条件 |
|---|---|---|
| 1 | 素材の種別、会議の基本情報、**出席者**、**案件の決めごと**、**崩れ候補** | 日付・相手先・出席者が埋まり、決めごとが全件確定し、崩れ候補が全件判定された（★承認） |
| 2 | 作業スペース | パスが解決し、素材がそこに置かれた |
| 3 | **議事録（成果物）と作業メモ** | 成果物に未確定が無く、決定事項と確認事項に担当が入った |
| 4 | 検査の結果表 | 全検査項目が「合格」か「要確認」で、要確認が利用者に渡った |
| 5 | 渡す形 | 相手へ出す版を確定した（★承認） |

## 1 素材と基本情報を確定する ★ここで止まる

`references/10_intake.md` を読む。素材が文字起こしか手書きメモかで読み方が変わる。

### 必須と任意

**必須が埋まるまで本文を書かない。** 無いまま進めると、もっともらしい値が埋まって出てくる。

| 区分 | 項目 | 無いとどうなるか |
|---|---|---|
| **必須** | 会議日 | 日付の無い議事録は、後から順序が追えず証拠にならない |
| **必須** | 相手先の名称 | 誰との約束か特定できない |
| **必須** | 素材そのもの（文字起こし or メモ） | 作業が成立しない |
| **必須** | 出席者 | **トランスクリプトを全文読んでから書く。**下記の規約に従う |
| 任意 | 会議名・議題 | 既定は素材から推定し、推定と明記する |
| 任意 | 前回議事録 | 不在なら「前回からの持ち越し」の節を作らない。不在そのものが情報 |
| 任意 | **書式の出所** | 既定は**このスキルの型**。探す順序は `20_template.md` 1節。既存書式があるのに型を当てると、受け取る側が読む場所を探すことになる |

**必須の4つが揃っていないときだけ聞く。** 任意の項目は既定で進め、
埋めた根拠（素材のどこから読んだか／推定か）を1行添える。

### 出席者を確定する

**話者ラベルだけで決めない。** 発言しない出席者がいる。
ラベルから作ると、**黙っていた人が議事録から消える。**

| 守ること | 外すとどうなるか |
|---|---|
| **トランスクリプトを全文読む** | 途中で一度だけ発言した人を落とす |
| **呼びかけや言及からも拾う**（「○○さんはどう思いますか」） | 発言が無い出席者を落とす |
| **テンプレートや前回の出席者を写さない** | 実際と違う名前が載り、修正が必要になる |
| **所属（部署）も素材から確認する。写さない** | 所属が実際と違うと、利用者が修正することになる |
| **所属が素材から分からなければ、書かずに聞く** | 推測の部署名が載る |
| **出席していない人を書かない** | 出ていない人が出たことになる |
| 読み取れないときは**利用者に聞く** | 推測の名前が載る |

**出席者の範囲は案件の決めごと**（下記の表）。既定は全員載せる。

### 案件の決めごとを確定する ★この表を出力する

**案件ごとに変わるものを、スキルの規約として扱わない。**
ある案件でそう決まったことを規約にすると、前提が違う案件で誤りとして効く。

**この表を埋めて出力する。** 既定で進めてよいが、**何を既定で埋めたかを出す。**
出さないと、確認したのか既定で通したのかが後から分からない。

| 決めごと | 既定 | 今回の値 | 出所 |
|---|---|---|---|
| 出力形式（md / Word / Excel） | **既存書式の形式に従う。無ければ md** | | **未確認** |
| **出力先のフォルダ** | **作業スペースの案件ディレクトリ。**案件で指定があればそこ | | **未確認** |
| 先方版に載せる範囲 | **相手先の指定があればそれに従う。無ければ決定事項と確認事項** | | **未確認** |
| 社内用の分け方（区切り線 / 別ファイル / 社内用なし） | **区切り線。**先方送付時に削除する | | **未確認** |
| **区分・出所の列を成果物に付けるか** | **付けない。**判断は作業メモに残す | | **未確認** |
| **記録形式（要約 / 会話の記録）** | **要約。**論点ごとに結論を書く | | **未確認** |
| 次回報告に使う材料を整理するか | する | | **未確認** |
| **前回のファイルをベースにするか** | **しない。**新規に作る | | **未確認** |
| **出席者の範囲** | **全員載せる** | | **未確認** |
| **内訳・詳細を載せるか** | **載せる** | | **未確認** |
| **確認事項を成果物に載せるか** | **載せる**（省くなら作業メモへ） | | **未確認** |
| **図を載せるか** | **素材に図が無ければ載せない。**図があるときは**聞く。**表に起こすのは指示があるときだけ | | **未確認** |
| **記録担当** | **素材から読み取る。**指定があればその人 | | **未確認** |

**既定は「未確認」。** 空欄にすると、見ていないことと既定で決めたことが区別できない。

**確定したら `formats/<相手先>.md` に残す。** 同じ相手先の次回は聞かずに引ける。
**残さないと毎回聞くことになり、確認の回数だけが増える。**

### 決めごとを規約にしない

**過去の案件でそう決まったことを、次の案件の前提にしない。**
`formats/` に残すのは**その相手先の決めごと**で、別の相手先には当てない。

| 例 | 誤った一般化 |
|---|---|
| 相手先が「決定事項と確認事項のみでよい」と言った | **全案件で議事を削る。**言われていない相手先にも適用してしまう |
| ある案件でホワイトボードを表に起こすよう指示された | **毎回表に起こす。**指示が無い案件でも手間をかける |
| ある案件が Excel だった | **全案件を Excel にする。**md でよい案件まで重くなる |
| ある案件で区分・出所の列が不要とされた | **全案件で付けない。**根拠を残したい案件でも落ちる |
| ある案件で前回のファイルに回を足す運用だった | **毎回前回を探す。**初回の案件で止まる |

**迷ったら既定で進め、出力の表に「既定で埋めた」と書く。** 聞かずに進めてよい。

### 書式の出所を決める

**このスキルの型は既定であって、優先ではない。** 相手先や社内に書式があるなら
そちらに合わせる。探す順序と、合わせても落とさない3つは `20_template.md` 1節。

**勝手に型を当てない。** 既存書式を無視した議事録は、受け取る側が
読む場所を探すことになり、章立てを揃えている意味が消える。

ただし**書式に合わせても、区分・出所・要確認の3つは足す。** 書式に列が無ければ
別表として添える。ここを落とすと、言った言わないを防ぐという目的そのものが消える。

**書式を①③で得たときは、`formats/<相手先>.md` に写す。** 次の案件が②で引けるようになる。
**写さないと `formats/` は永久に空で、毎回雛形を渡してもらうことになる。**

| 出所 | 写すか |
|---|---|
| ① 渡された雛形 | **写す。**同じ相手先の次回に効く |
| ③ 過去の議事録から読み取った | **写す。**読み取りをやり直さずに済む |
| ② `formats/` から引いた | 写さない。既にある |
| ④ 無し（スキルの型） | 写さない。相手先の書式ではない |

写すのは**章立て・列・呼称**だけで、**その回の会議の内容は写さない。**
内容を写すと、次の案件で前回の中身が混ざる。

### 崩れた語を洗い出す

**崩れ候補が1件でもあれば `references/15_terms.md` を読む。**
自動文字起こしの誤変換と、手書きメモの略記は、**読める語に化けるため気づかれない。**

やることは3つ。**そのまま載せて終わりにしない。**

1. 崩れ候補を5つの型で洗い出す
2. **案件の分野を特定し、分野の語彙を調べる**
3. **候補を2つ以上出し、合否を利用者に問う**（判定の既定は「未確認」）

**調べたから直してよいのではない。** 確定させるのは利用者で、
候補が1つしか出なかった場合も問うのを省かない。

**崩れ候補が未確認のままでも、議事録の下書きは出す。** 語の確定を待つと、
記憶が新しいうちに相手と突き合わせる機会を失う。下書きを先に出し、並行して確定させる。

### 止まる理由

日付・相手先・出席者は後続すべての前提になる。間違えると本文を全部書き直すことになり、
しかも**間違えたまま相手に出すと、訂正の連絡が必要になる。**

**止まるときは、この時点で未決のものを全部まとめて出す。**
基本情報の確認、**書式の出所**、**崩れ候補の合否**、素材の読み取りで判然としなかった箇所を、
同じメッセージに載せる。承認1件につき1ターンを使わない。

**崩れ候補の合否を別のターンで聞かない。** 承認ポイントはこの1箇所のままにする。
増やすと利用者が承認作業員になる。

## 2 作業スペースを用意する

`references/30_export.md` の「作業スペース」の節を読む。

**議事録と素材はスキルフォルダに置かない。** スキルフォルダは手順を置く場所で、
案件の記録を置く場所ではない。パスはスクリプトで解決する。

```bash
SKILL_DIR=<この SKILL.md があるディレクトリの絶対パス>
cd "$SKILL_DIR" && ./scripts/ws-path.sh <YYMMDD_PJ名>
```

**`cd` を省かない。作業ディレクトリは呼び出しごとに戻るため、相対パスだけでは外れる。**

解決できなかったら**止めて報告する。** 既定の場所へ落とさない。
落とすと書けたことになって、不発に気づけない。

この手順は聞かずに進める。既存の案件ディレクトリがあればそれを使い、
無ければ作って、どちらをしたかを1行述べる。

## 3 本文を書く

### 決定事項と議事の位置づけ ★ここを外すと振り分けを誤る

**何をどちらに書くかは、この2つの軸で決める。**

| 節 | 軸 |
|---|---|
| **決定事項** | **進め方として、または進めるうえで行うこととして決まったか** |
| **議事** | **今どこにいるか**と**次にどう進めるか** |

**決定事項の判断は「先方が了承したか」だけではない。**
進め方として決まったことと、進めるうえで行うことを含む。

| 決定事項に入れる | 議事に入れる |
|---|---|
| **担当者個人の作業も入れる。**「I が今日中に KPI の算出に必要な情報をまとめる」 | **報告された数値や状況。**「関連項目は11項目」 |
| 進め方そのものの合意 | 現状の説明、経緯 |

**議事の軸は「何が話されたか」ではない。** 話された順に並べると、
今どこにいるかが読み取れない。**立ち位置と次の進め方で組み立てる。**

**読み手は、出席していない人に限らない。** 出席者も、段取りを共有するために読む。
「出席していない人向け」と考えると、出席者が知っている前提のことを落とす。

- **行き過ぎると:** 作業をすべて決定事項に入れて、決定事項が作業一覧になる。
  **決まっていない作業は入れない**

### 型と書き方を読む

`references/20_template.md` を読む。**手順1で決めた決めごとに従って書く。**
既存書式に合わせる場合の規約、事実・意向・留保の分離規約、見本がある。

`references/25_writing.md` を読む。**書き方の禁止と、原文で確かめる工程がある。**

### 書き方

**議事録としてまとめる。箇条書きの羅列にしない。**

| 守ること | 悪い | 良い |
|---|---|---|
| **論点ごとに結論を書く** | 発言を順に並べる | 論点を立て、その結論を1行で書く |
| **会話文のまま書かない** | 「○○部長: 〜と述べた」「では、書いておく」 | 「〜は、これから調べる必要がある」 |
| **望む状態は意向として書く** | 「要望: 〜が見える表を早く」 | 「○○室長のイメージ: 〜が分かる表」 |
| **個人名は既定では書かない** | 全発言に名前を付ける | **その人の発言であることが結論を変えるときだけ**名前を出す |
| **区分の注記を本文に付けない** | 「（認識）」「（要確認）」を文末に付ける | 注記を付けず、判断は作業メモに残す |

**立場と個人名は別の水準。** 立場（自社／先方）が分からないと読めないので必ず書く。
個人名は、役職者の明言や責任の所在が論点になるときだけ。
**先方へ出す版では、個人名を書かず立場だけにしてよい。**

### 載せないもの

**重要でない発言を載せない。** 載せると、読む人が何が論点か探すことになる。

| 載せない | 例 |
|---|---|
| 相手の理解度への感想 | 「理解していただけたようだ」 |
| 伝え方の反省 | 「説明が足りなかった」 |
| 接続確認のやりとり | 「聞こえますか」「画面は見えていますか」 |
| 挨拶、世間話、休憩 | — |
| **憶測** | 素材に無い前提、推測した経緯 |

**載せなかった発言は作業メモに残す。** 後から「なぜ入っていないのか」と問われたときに答えられる。

- **行き過ぎると:** 論点に関わる発言まで「重要でない」として落とす。
  **判断に迷ったら載せる。**落とすのは上の5つに当たるときだけ

### 済んだことは「済み」と書く

**会議中に完了したものを「〜する」と書かない。** 未実施に見えて事実と食い違う。

| 悪い | 良い |
|---|---|
| 該当項目にマーカーを付ける | 該当項目にマーカーを付けた（**済み**） |

**その場で終わったかどうかを素材から確かめる。** 確かめられないなら、
作業メモに「完了したか未確認」と残し、成果物には書かない。

### 納期が分からないものは「確認中」

**推測の日付を入れない。** 「不明」とも書かない。成果物に未確定を置かないため。

| 状態 | 書き方 |
|---|---|
| 日付が決まっている | その日付 |
| **決まっていない** | **確認中** |
| そもそも納期の概念が無い（済んだこと） | — |

### 5値で埋める

**すべての項目に、次の5つのいずれかを付ける。「判定不能」を合格に数えない。**

| 値 | 意味 |
|---|---|
| **決定** | **相手先と握った。**条件も留保も無い。ここに書けるのは握ったレベルだけ |
| **認識** | **そう理解しているが、握ってはいない。**確実でないものはここ。条件付きの合意もここ |
| **未決** | **決めなければ進まない。**担当と期限を書く。確認事項に出す |
| **要確認** | 素材の記述が曖昧で、どちらとも読める。**利用者に問う対象** |
| **不明** | 素材に記述が無い。**推測で埋めず、この値を書く** |

**「決定」と「認識」を混ぜない。** 混ぜると、握っていないことを握ったものとして
相手に出すことになり、次の打合せで崩れる。**確実でないなら「認識」に落とす。**

**「不明」を空欄にしない。** 空欄は「書き忘れ」と区別できないため、
後から読んだ人が「議題に出なかった」と誤解する。

### 判断を作業メモに出す

**区分の判断は、作業メモ（`notes.md`）に必ず現れる。** 内部で判断して残さない、をしない。
区分・出所の列を成果物に付けるかは決めごとだが、**付けない場合も判断は作業メモに書く。**

| 置き場所 | 何を |
|---|---|
| 作業メモ（常に） | 論点ごとの区分、出所、確認待ち、載せなかった発言 |
| 成果物（決めごとが「付ける」のときだけ） | 区分・出所の列 |

**最後に、作業メモの区分が空の論点が1つも無いことを確認する。**
残っていたら手順3は完了していない。**成果物だけ見て完了にしない。**

## 4 出す前に検査する

`references/40_review.md` を読み、**検査の結果を表として出力する。**
検査したと書くだけにしない。やったかどうかが外から見えないため、飛ばされる。

各項目の判定は3値。**既定は「未確認」。**

| 判定 | 意味 |
|---|---|
| 合格 | 確かめて、問題が無かった |
| **要確認** | 利用者に確かめてもらう必要がある。**落とさずに渡す** |
| **未確認** | まだ見ていない。**これが残っていたら手順4は終わっていない** |

**「要確認」を落とさない。** 要確認を削ると、曖昧な箇所が確定したことになって内容が曲がる。
判定を5値にしている理由と同じで、**消すのではなく渡す。**

## 5 渡す形を決める ★ここで止まる

`references/30_export.md` の「渡す形」の節を読む。

**形式は手順1で決めた値を使う。** ここで既定を作り直さない。

| 渡すもの | いつ | 委譲先 |
|---|---|---|
| 議事録本体 | **常に作る。**形式は決めごとの値 | md はこのスキル。Word は `docx`、Excel は `xlsx` |
| 先方版 | 相手先へ出すとき。**載せる範囲は決めごと** | 同上 |
| 確認事項の進捗管理表 | 要求されたときだけ | `xlsx` スキル |
| 中間物（整理前の発言リスト） | **渡さない** | 作業スペースに残すだけ |

**形式ごとの体裁は `30_export.md` にある。選んだ形式の行だけを読む。**
Excel なら枠線、セルを分ける、図表は右。**他の形式の条項を当てない。**

**相手へ出す版を確定する直前で止まる。** 外部に出たものは取り消せない。
止まるときは、検査の「要確認」が残っていればそれも同じメッセージに載せる。
### 修正の進め方

**先に直さない。** 直し方を示し、承認を得てから直す。

| 守ること | 外すとどうなるか |
|---|---|
| **「どう直すか教えて」と言われたら、案を出して止まる** | 直してしまうと、承認の意味が無くなる |
| **上書きする前に、そのファイルが編集中でないかを確認する** | **利用者が開いたまま編集していると、上書きで修正が消える。**戻せない |
| **利用者が自分で直した箇所を再修正しない** | 直したものを元に戻すことになる |

**編集中かどうかは、利用者に聞いて確かめる。** 開いているかを機械で判定しない。
判定を誤って上書きすると不可逆。

**利用者が直した箇所は、作業メモに記録する。** 次回に同じ直しをしないため。

### 委譲するときの作法

**docx・xlsx の作り方をここに書き直さない。** 委譲先が持っている機能であり、
2箇所に書くと片方だけ古くなる。渡すのは確定した中身と、出力先のパスと、
上の体裁の指定だけ。

**委譲先の作法と、このスキルの規約が食い違ったら、このスキルの規約を採る。**
食い違った箇所とどちらを採ったかを報告する。黙って片方に寄せない。
実際に起きたのは、記入例として架空の行を求められた件で、
**入れると議事録と件数が食い違う**ため入れなかった。

## 完了したら次を提案する

報告して止まらない。次の行動を分類して出し、**推奨を1つ示して理由を述べる。**

| 分類 | 例 |
|---|---|
| A 外に出す | 相手先へ送る版（docx）を作る、社内へ共有する |
| B 次の作業 | 確認事項を進捗管理表にする、次回の議題案を作る |
| **C 調べる** | 前回議事録を探して持ち越しを突き合わせる、相手先の呼称の決めごとを確認する |
| D 前工程に戻る | 素材に欠けがあり、出席者に確認を依頼する |
| E 止める | 相手の確認待ち、社内承認待ち |

**C を忘れやすい。** 要確認が残っているときは、本文を直すより前回議事録を探す方が速い。

## 人にしかできない工程

**スキルが自分でやったことにしない。**

| 工程 | 誰がやるか | 依頼の文面と、結果の反映先 |
|---|---|---|
| 素材に無い発言内容の確認 | 出席者本人 | 「<日付>の<相手先>との打合せで、<論点>はどう決まりましたか」と聞く。回答は本文の該当行の区分を「決定」か「未決」に更新する |
| 相手先との認識合わせ | 利用者 | 確定前の md を相手に送って確認を求める。相手の訂正は本文に反映し、訂正された旨を残す |
| 送付・提出 | 利用者 | スキルは出力までで、送信はしない |

**依頼して終わりにしない。** 受け取った結果をどこに反映するかまで上の表に書いてある。

## 外部依存

| 依存 | 要るとき | 無いときどうするか |
|---|---|---|
| `docx` スキル | Word 出力を求められたとき | md のまま渡し、Word 化できないと報告する |
| `xlsx` スキル | Excel 出力を求められたとき | md の表のまま渡す |

文字起こし済みのテキストを受け取る前提で作ってある。

## 不一致を見つけたとき

本文に書いてあるパスや前提が、実際と違っていたら**そこで止まる。**
`SKILL.md` と `references/` を直さない。

報告するのは3つ。**直し方は提案しない。**

| 項目 | 内容 |
|---|---|
| 本文の記述 | ファイル名と行、書いてある通りの文言 |
| 実際 | 確認した結果 |
| この案件への影響 | 続行できるか、できないか |

直すのはスキルを作る・直すセッションの役目。使う側が直すと、その案件では正しくても
別の案件で壊れ、しかも原因の台帳に記録が残らず件数が数えられない。

**行き過ぎると:** 止まるだけで何も報告せず、案件が進まなくなる。
**止まるときは必ず上の3項目を出す。** 出せないなら止まらずに続ける。

## 改善プロトコル

このスキルの手順どおりに進められなかった場合、または利用者から出力への指摘を受けた場合、
以下を順に行う。

1. 台帳の表に1行追記する（日付／依頼の要約／期待した挙動／実際の挙動／推定原因）。
   台帳は**スキルディレクトリの2つ上**の `local/docs/feedback.md`。
   追記はこのファイルに対してのみ行う。

2. `SKILL.md` および `references/` はこの時点では書き換えない。

3. 利用者から明示的に修正を求められた場合のみ、`skill-builder` スキルに渡して改訂する。

4. **台帳が存在しない、または書き込めない環境では何もしない。**
   エラーを報告せず、代替手段も取らない。台帳は改訂する側が持つもので、
   スキルだけを受け取った環境には無いのが普通。
